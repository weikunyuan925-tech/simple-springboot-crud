## 6. 逐项动态验证

### 6.1 VUL-01 [严重] 所有用户接口完全缺失认证

**测试原理**：项目未引入 `spring-boot-starter-security`，没有 `SecurityFilterChain`、过滤器或方法级鉴权，请求进入 Controller 前没有身份认证环节。
**预期结果**：不带任何凭据的匿名请求应返回 200/201，而不是 401/403；响应不应包含 `WWW-Authenticate`。

#### 6.1.1 匿名读取

```bash
curl -i --noproxy '*' http://127.0.0.1:18080/api/users
curl -i --noproxy '*' http://127.0.0.1:18080/api/users/1
```

| 请求 | 实际响应 | 预期 | 判定 |
|---|---|---|---|
| `GET /api/users` | `200`，`total=5`，返回全部用户 PII；无 `WWW-Authenticate`、无 `Set-Cookie` | 200/未认证应被拒 | 确认匿名可读 |
| `GET /api/users/1` | `200`，返回 John Doe 的姓名、邮箱、电话 | 同上 | 确认匿名可读 |

#### 6.1.2 匿名写入/删除

```bash
curl -i --noproxy '*' -X POST http://127.0.0.1:18080/api/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"VUL01 Anon","email":"vul01-create-<ts>@example.test","phone":"010-0000-0001"}'

curl -i --noproxy '*' -X PUT http://127.0.0.1:18080/api/users/7 \
  -H 'Content-Type: application/json' \
  -d '{"name":"VUL01 Anon Updated","email":"vul01-create-<ts>@example.test","phone":"010-0000-0002"}'

curl -i --noproxy '*' -X DELETE http://127.0.0.1:18080/api/users/7
curl -i --noproxy '*' http://127.0.0.1:18080/api/users/7
```

| 步骤 | 实际响应 |
|---|---|
| 匿名 POST | `201`，创建 ID=7，`message=User created successfully` |
| 匿名 PUT | `200`，ID=7 被修改为 `VUL01 Anon Updated` |
| 匿名 DELETE | `200`，`userId=7` |
| 删除后 GET | `404`，`User not found with id: 7` |

**实际结果**：全程未发送 `Authorization`、Cookie 或任何凭据，读、写、删全部成功。
**判定：已确认（VUL-01 成立）。**

### 6.2 VUL-02 [严重] 对象级/功能级授权缺失（BOLA/IDOR）

**测试原理**：Controller 直接把路径中的 `id`/`email` 传给 Service，Service 直接按该键查询；实体没有 `ownerId`/`tenantId`，代码中没有“当前用户”上下文或归属校验。
**预期结果**：匿名者可以读取任意对象、修改任意对象、删除任意对象；不存在 ID/邮箱返回 404。

#### 6.2.1 任意对象读取与枚举

```bash
curl -i --noproxy '*' http://127.0.0.1:18080/api/users/1
curl -i --noproxy '*' http://127.0.0.1:18080/api/users/email/john.doe@example.com
curl -i --noproxy '*' 'http://127.0.0.1:18080/api/users/search?name=%25'
curl -i --noproxy '*' http://127.0.0.1:18080/api/users/9999
```

| 请求 | 实际响应 | 说明 |
|---|---|---|
| `GET /api/users/1` | `200`，返回用户 1 的 PII | 任意 ID 可读 |
| `GET /api/users/email/john.doe@example.com` | `200`，返回用户 1 | 任意邮箱可读 |
| `GET /api/users/search?name=%` | `200`，`total=5` | 通配符一次读取全部用户 |
| `GET /api/users/9999` | `404` | 与存在对象可区分 |
| `GET /api/users/email/nobody@example.com` | `404` | 可据此枚举邮箱 |
| ID 遍历 1–5 / 9999 | `200` × 5 / `404` | 自增 ID 可直接遍历 |

#### 6.2.2 任意对象修改与删除

# 创建一次性"受害者"用户
curl -i --noproxy '*' -X POST http://127.0.0.1:18080/api/users \

# 匿名修改

  -d '{"name":"VUL02 Victim Updated","email":"vul02-victim-updated-<ts>@example.test","phone":"010-0000-0004"}'

# 匿名删除

| 步骤 | 实际响应 |
|---|---|
| 创建受害者 | `201`，ID=8 |
| 匿名 PUT | `200`，name/email/phone 均被修改 |
| 读取修改后对象 | `200`，返回修改后的值 |
| 匿名 DELETE | `200`，`userId=8` |
| 删除后 GET | `404` |

**实际结果**：匿名者可对任意路径 ID 的对象执行读取、修改、删除，未出现 403。

**如实说明（不强行认定经典 IDOR）**：经典 IDOR 指“已认证用户 A 访问用户 B 的对象”。本项目没有任何认证、登录、令牌或主体概念，因此无法构造两个已认证主体的越权场景。本测试证明的是更严重的“匿名 + 任意对象操作”，其漏洞模式与 IDOR 一致，但不应表述为“已完成经典 IDOR 双身份复现”。

### 6.3 VUL-03 [高] CORS 允许任意 Origin

**测试原理**：`UserController` 类级 `@CrossOrigin(origins = "*")` 令 Spring 对任意 `Origin` 返回允许跨域读取的响应头；预检请求按接口映射放行方法。
**预期结果**：简单请求返回 `Access-Control-Allow-Origin: *`；DELETE/PUT 预检返回 200，并包含对应方法。

```bash
curl -i --noproxy '*' -H 'Origin: https://evil.example' \
  http://127.0.0.1:18080/api/users

curl -i --noproxy '*' -X OPTIONS http://127.0.0.1:18080/api/users/1 \
  -H 'Origin: https://evil.example' \
  -H 'Access-Control-Request-Method: DELETE' \
  -H 'Access-Control-Request-Headers: content-type'

curl -i --noproxy '*' -X OPTIONS http://127.0.0.1:18080/api/users/1 \
  -H 'Origin: https://evil.example' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type'
```

| 请求 | 实际响应头 |
|---|---|
| 简单 GET | `200`；`Access-Control-Allow-Origin: *`；`Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers` |
| DELETE 预检 | `200`；`Access-Control-Allow-Origin: *`；`Access-Control-Allow-Methods: DELETE`；`Access-Control-Allow-Headers: content-type`；`Access-Control-Max-Age: 1800` |
| PUT 预检 | `200`；`Access-Control-Allow-Origin: *`；`Access-Control-Allow-Methods: PUT`；`Access-Control-Allow-Headers: content-type`；`Access-Control-Max-Age: 1800` |

- 未返回 `Access-Control-Allow-Credentials: true`（`@CrossOrigin` 默认 `allowCredentials=false`）。
- 未执行浏览器实测。

**判定：HTTP 响应头层面已确认 CORS 策略为任意 Origin 放行；浏览器实际可利用性未验证。**

**浏览器侧分析（不将 curl 结果等同于浏览器可利用性）**：
- 通配符 ACAO 且不带凭据时，其他 Origin 的 JavaScript 可以读取响应内容；
- 当前 API 没有认证，因此不存在可被浏览器自动携带的 Cookie/凭据，CORS 通配符的增量影响主要是“恶意页面可跨域读取本机 localhost 数据”；
- 浏览器 Private Network Access（PNA）策略可能拦截公网页面访问回环地址，因此实际可利用性取决于浏览器版本和策略；
- 真正验证需要从另一个 Origin 提供页面并执行 `fetch('http://127.0.0.1:18080/api/users')`，观察响应是否可读、预检是否通过。本阶段未执行该测试。

### 6.5 VUL-05 [中] 批量赋值残余与死代码

**测试原理**：
- POST 绑定 `UserCreateRequest`，该类没有 `id` 字段；Spring Boot 默认的 Jackson 配置忽略未知属性，因此 body 中的 `id` 被静默忽略，`save()` 走 `persist()` 新建，ID 由数据库生成；
- PUT 绑定含 `id` 的 `UserDTO`，但 Service 先用路径 ID 查询、只复制 `name/email/phone`，body 中的 `id` 不参与定位；
- 工作区已删除 `convertToEntity()` 死代码。

**预期结果**：
1. POST 带 `"id":1` → 201，新 ID（应为 6），用户 1 不变；
2. PUT 用户 6 但 body `"id":2` → 200，修改用户 6，用户 2 不变；
3. 编译产物中不存在 `convertToEntity()`。

#### 6.5.1 POST 带 id=1

```bash
curl -i --noproxy '*' -X POST http://127.0.0.1:18080/api/users \
  -H 'Content-Type: application/json' \
  -d '{"id":1,"name":"VUL05 Create","email":"vul05-post-<ts>@example.test","phone":"010-0000-0005"}'
```

实际响应：`201`，返回 `user.id=6`，`name=VUL05 Create`。
用户 1 修改前后逐字节对比：**UNCHANGED**。

#### 6.5.2 PUT 路径 ID 与 body ID 不一致

```bash

```

实际响应：`200`，返回 `user.id=6`，`name=Path Id Wins`。
用户 2 修改前后逐字节对比：**UNCHANGED**。

**实际结果**：
