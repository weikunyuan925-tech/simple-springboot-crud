## 2. 测试目的

验证系统在 JWT 身份认证基础上，是否正确实施对象级访问控制，防止普通用户通过修改资源 ID、邮箱或搜索条件访问其他用户的数据。

本轮重点验证：

1. 用户只能读取自己拥有的资料。
2. 用户不能通过列表接口获取其他用户的资料。
3. 用户不能通过邮箱查询其他用户的资料。
4. 用户不能通过姓名搜索获取其他用户的资料。
5. 用户不能修改其他用户的资料。
6. 用户不能删除其他用户的资料。
7. 用户创建资料时，不能通过客户端提交伪造的 ownerId 改变资料归属。

## 3. 测试账号与数据

测试创建两个独立的普通用户：

| 用户   | 用户名      | 角色 | 资料邮箱                                          |
| ------ | ----------- | ---- | ------------------------------------------------- |
| 用户 A | auth_user_a | USER | [auth-a@example.test](mailto:auth-a@example.test) |
| 用户 B | auth_user_b | USER | [auth-b@example.test](mailto:auth-b@example.test) |

两名用户分别拥有独立的用户资料，用于模拟不同身份之间的越权访问。

测试过程中通过数据库实际生成的 ID 定位资料，不依赖固定 ID。

## 5. 安全控制机制核查

结合项目代码，本轮重点验证以下控制机制：

### 5.1 当前用户身份获取

业务服务通过 Spring Security 的 SecurityContext 获取当前登录用户，并根据用户名查询对应的 SysUser。

### 5.2 对象级数据隔离

资料查询、修改和删除操作均使用当前用户 ID 作为数据访问条件，避免仅凭资料 ID 操作其他用户的数据。

### 5.3 列表和搜索隔离

列表查询和姓名搜索均限定当前用户的数据范围，防止通过批量查询或搜索接口泄露其他用户资料。

### 5.4 创建资料的所有权控制

创建资料时，所有者由服务端根据当前登录身份设置，而不是直接信任客户端提交的 ownerId。

## 7. 测试结论

本轮 T4 共执行 8 项对象级授权与越权访问测试，全部通过。

在本轮覆盖的用户资料业务接口和测试场景中，未发现跨用户读取、修改、删除资料的问题，也未发现通过伪造 ownerId 改变资料归属的问题。

本轮测试结果表明，当前项目在已覆盖场景中能够正确实施基于当前登录用户的对象级数据隔离。

**测试范围说明：**

本报告主要验证对象级授权（BOLA/IDOR）问题，不代表已经完成完整的 RBAC 角色权限测试。由于当前项目没有明确的 ADMIN 专属业务接口，本轮未验证管理员与普通用户之间的管理功能权限边界。
